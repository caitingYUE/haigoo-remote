# Haigoo 小程序企业联系人、申请方式与关注管理设计规格

- 日期：2026-09-05
- 状态：已完成对话评审，待书面规格复核
- 设计路径：Architectural
- 适用范围：微信小程序企业目录、统一企业详情、岗位详情、个人中心关注企业管理

## 1. 背景与问题

当前小程序已有企业目录、Match、企业详情、岗位详情、关注企业和微信提醒能力，但五条链路尚未形成一致的数据与交互契约：

1. 岗位详情只消费官网链接，已由数据层提供的公开申请邮箱没有进入页面操作区。
2. 企业详情已实现会员联系人列表和数量锁定态，但服务端不给非会员返回脱敏预览，因此体验版无法展示姓名与 title。
3. 企业目录根据岗位标题在前端猜测角色标签，容易混入综合分类和粗粒度分类，并把整句岗位摘要统一染成橙色。
4. Match 与企业目录虽然进入同一路由，但访问参数、企业数据映射和页面状态缺少明确的单一契约，实际呈现容易产生入口差异。
5. 个人中心的“关注企业”直接进入企业目录，无法集中区分关注和微信提醒，也无法高效取消关注或关闭提醒。

本次设计用现有服务和页面为基础，收敛为一套企业数据契约与一个企业详情实现。不会修改推荐算法、Match 排序、会员套餐、微信模板配置、底部 TabBar 或无关页面。

## 2. 目标与成功标准

### 2.1 用户目标

- 仅提供邮箱的岗位仍有明确、可用的公开申请入口。
- 非会员能知道企业已收录哪些类型的联系人，但无法获取邮箱、LinkedIn 等隐私联系方式。
- 会员能在同一区域查看和复制完整联系人信息。
- 企业列表只强调与用户求职方向相关的具体岗位分类。
- 从 Match、企业列表或关注页进入同一企业时，看到相同的企业资料、联系人、岗位和订阅状态。
- 用户能在个人中心独立管理关注与微信提醒。

### 2.2 数据与权限目标

- 公开申请邮箱与会员联系人严格分离，公开申请方式不受会员权限限制。
- 非会员联系人响应不包含原始姓名、邮箱或 LinkedIn，脱敏在服务端完成。
- 角色标签来自后台岗位分类字段，不在小程序端根据标题猜测。
- 关注和订阅保持两个独立状态；取消关注由服务端原子地关闭订阅并移除关注。
- 已关注企业即使随后停止招聘，用户仍能进入其公开详情并管理关注。

### 2.3 上线目标

- 旧版客户端可以忽略新增字段继续工作。
- 新版客户端遇到尚未升级的体验版后端时稳定降级，不崩溃、不展示虚构数据。
- 匿名、登录非会员、有效会员和过期会员均有明确状态。

## 3. 方案选择

采用“扩展现有企业契约并统一消费”的方案：

- 保留现有 `/mini/companies`、`/mini/companies/:id`、`/mini/companies/:companyId/jobs/:jobId` 和 `/mini/match/follows` 路由。
- 在现有响应中增加受控字段，不新建平行的企业详情接口。
- Match、企业目录和关注页只传企业 ID，并由统一详情页请求权威数据。
- 新增个人中心二级页面承载关注管理，不新增底部 Tab。

不采用以下方案：

- 不做纯前端补丁，因为前端无法安全生成联系人预览，也无法获得权威细分类。
- 不建立新的完整企业领域服务，因为本次已有稳定接口和组件可复用，大规模重构会扩大发布风险。
- 不在客户端缓存或推断会员权限，不把敏感原始联系人发送给非会员后再隐藏。

## 4. 公开申请方式

### 4.1 数据来源

岗位详情继续使用既有字段：

```ts
interface MiniCompanyJobDetail {
  officialApplyUrl: string
  publicApplicationEmail: string
}
```

CloudRun 保持现有规则：

- 合法的 HTTP/HTTPS 地址写入 `officialApplyUrl`。
- 没有合法链接且 `hiringEmail` 是合法邮箱时，写入 `publicApplicationEmail`。
- 不把企业联系人中的任意邮箱自动当成岗位申请邮箱。

### 4.2 页面状态

岗位详情在正文后、固定操作栏之前展示“申请方式”：

| 数据状态 | 页面内容 | 主操作 |
| --- | --- | --- |
| 有官网链接 | 官网申请 | 复制申请链接 |
| 仅有公开邮箱 | 展示完整公开申请邮箱 | 复制申请邮箱 |
| 两者都没有 | 暂未收录公开申请方式 | 禁用状态 |

当前服务端规则只会在没有链接时返回公开申请邮箱，因此页面无需处理两个公开入口竞争。未来若响应同时包含两者，官网链接优先作为主操作，邮箱作为第二公开方式展示。

复制成功反馈必须区分“申请链接已复制”和“申请邮箱已复制”。申请邮箱属于企业公开招聘渠道，不要求会员，也不进入企业联系人会员卡。

## 5. 企业联系人权限契约

### 5.1 类型

新增只包含安全字段的预览类型：

```ts
interface CompanyContactPreview {
  id: string
  maskedName: string
  title: string
}

interface MemberOnlyContact {
  id: string
  name: string
  title: string
  email: string
  linkedin: string
}
```

企业详情响应增加：

```ts
interface MiniCompany {
  contactCount?: number
  contactPreviews?: CompanyContactPreview[]
  contacts?: MemberOnlyContact[]
}

interface CompanyAccess {
  contacts: boolean
  contactPreview: boolean
}
```

### 5.2 服务端脱敏

服务端从有效联系人记录生成预览，前端不参与脱敏：

- 中文姓名：保留第一个汉字，其余字符统一为 `*`，例如 `张三 -> 张*`、`欧阳娜娜 -> 欧***`。
- 英文及空格分隔姓名：每个非空词保留首字符并统一追加三个 `*`，不暴露原词长度，例如 `Jane Smith -> J*** S***`。
- 单字符姓名显示原字符；空姓名显示 `联系人`。
- title 经现有文本清洗后完整返回。
- 预览对象严禁包含 email、LinkedIn、原始姓名或其他可反推出联系方式的字段。

隐私安全测试必须检查序列化后的非会员响应，而不只检查 TypeScript 类型。

### 5.3 权限矩阵

| 用户状态 | `contactPreviews` | `contacts` | 页面表现 |
| --- | --- | --- | --- |
| 匿名或非会员 | 有联系人时返回 | 不返回 | 脱敏姓名 + title + 会员锁定入口 |
| 有效会员 | 可省略或同时返回 | 返回 | 完整姓名、title、邮箱/LinkedIn与复制操作 |
| 过期会员 | 有联系人时返回 | 不返回 | 与非会员一致 |
| 无有效联系人 | 空数组 | 空数组或不返回 | 暂未收录企业联系人 |

服务端生成企业联系人前，先汇总当前公开岗位中合法的 `publicApplicationEmail`。与公开申请邮箱相同的邮箱从会员联系人和联系人预览中排除，也不计入 `contactCount`。`trusted_companies.hiring_email` 只有在它不是任何公开岗位的申请邮箱、且确实作为企业联系线索存在时，才进入会员联系人。企业详情不得把公开申请邮箱重复显示为一条可解锁联系人，避免同一公开信息被错误收费。

## 6. 统一企业详情

### 6.1 单一入口

以下入口全部进入 `/pages/company-detail/index?id=<companyId>`：

- Match 企业卡片。
- 企业目录卡片。
- 关注企业管理页。

`search` 参数只用于非会员精确搜索的访问授权，不改变公司数据映射、样式、页签或联系人逻辑。企业详情不读取 Match 卡片摘要作为页面数据，也不创建入口专属的企业信息。

### 6.2 访问授权

非会员企业详情允许以下任一条件：

1. 企业属于免费目录。
2. 企业属于用户当前固定 Match 快照。
3. 企业命中本次精确搜索授权。
4. 用户对该企业存在有效关注记录。

第四条确保企业停止招聘后，关注页仍可打开其公开详情并取消关注。它不授予完整企业目录或联系人权限。

### 6.3 页面结构

以当前企业目录入口的企业详情为唯一基准：

1. 企业 Logo、名称、真实标签、行业与地点。
2. 真实评分、员工数、成立年份和开放岗位数；缺失字段显示现有中性占位或自然收起。
3. 概览、职位、文化页签。
4. 概览内顺序为：关于企业、企业联系人、热门职位。
5. 底部为订阅更新和官网链接操作。订阅按钮按关注与提醒状态显示“订阅更新”“开启微信提醒”或“关闭微信提醒”。

联系人状态：

- 有完整权限：按联系人逐项显示姓名、title、可用联系方式和复制操作。
- 有预览无权限：每项显示脱敏姓名与 title，整张区域具有锁定说明和“查看会员权益”入口。
- 无联系人：显示“暂未收录企业联系人”，不展示会员诱导卡。

企业详情沿用现有订阅入口，但其行为必须符合独立状态机：未关注用户点击“订阅更新”时先创建关注，再请求微信授权；用户拒绝或系统不可用时仍保留关注。已关注未开启提醒时显示“开启微信提醒”，已开启时显示“关闭微信提醒”；关闭提醒只关闭微信通知。企业详情不使用“取消订阅”执行取关，取消关注只能由明确的关注控件或关注管理页触发。

所有真实字段缺失时自然降级，不补写企业名称、标签、评分、地址、联系人或岗位。

## 7. 企业目录角色标签与个性化强调

### 7.1 权威字段

企业目录查询在开放岗位聚合中增加：

```ts
interface MiniCompany {
  openRoleCategories?: string[]
}
```

数据来自 `company_job_history.category`，并满足：

- 仅统计未关闭且 `is_public_opportunity = true` 的岗位。
- 只返回 `JOB_CATEGORY_OPTIONS` 白名单中的值。
- 服务端去重并按开放岗位的新鲜度与数量形成稳定顺序。
- 最多返回用于摘要的前若干项，客户端最终展示不超过两个。
- `role_families` 仅用于判断用户方向是否相关，不作为用户看到的细分类名称。

### 7.2 最细粒度规则

当同一企业的开放岗位产生包含关系或同组冲突时，优先保留更具体分类：

- `产品经理` 优先于由其推导出的 `产品` 家族标签。
- `前端开发`、`后端开发`、`全栈开发` 优先于 `软件开发`。
- `UI/UX设计`、`视觉设计` 等具体项优先于 `设计`。
- 已是白名单具体分类的值不再通过岗位标题改写。
- 无法映射到白名单时不猜测，摘要退化为“查看当前开放岗位”。

该规则应成为共享的纯函数并有独立测试，避免企业目录和 Match 分别维护分类逻辑。

### 7.3 用户方向匹配

用户匹配方向按以下优先级生成：

1. `WatchProfile.customRoleTerms` 中属于后台分类白名单的精确分类。
2. 精确项不存在时，使用 `WatchProfile.roleFamilies` 与每个分类对应的角色家族判断。
3. 用户尚未设置方向或职业档案未加载时，不高亮任何分类。

企业卡片岗位摘要由多个文本节点组成，而不是一个统一着色字符串。例如：

```text
产品经理、运营等可申请
```

- 与用户方向相关的“产品经理”“运营”使用品牌橙。
- 标点、未匹配分类和“等可申请”使用深灰色。
- 不只依赖颜色表达含义；整行读屏名称仍是完整自然语言。
- 最多展示两个分类，保持列表卡片高度稳定。

企业目录直接消费列表响应中的 `openRoleCategories`，不再为每家企业请求详情，也不再调用 `roleLabelsFromTitles` 猜测标签。

## 8. 关注企业管理页

### 8.1 导航与页面职责

新增个人中心二级页面 `/pages/followed-companies/index`：

- 个人中心“关注企业”数字入口改为 `navigateTo` 此页面。
- 不新增底部 TabBar 项。
- 页面负责查看关注列表、进入企业详情、开启/关闭微信提醒和取消关注。
- 企业目录继续负责发现与搜索，不承担个人关注管理。

### 8.2 关注列表契约

扩展现有 `GET /mini/match/follows` 响应，每项返回：

```ts
interface CompanyFollowSummary {
  company_id: string
  name: string
  industry: string
  logoFileId?: string
  logoUrl?: string
  openJobCount: number
  openRoleCategories: string[]
  followedAt: string | null
  wechat_enabled: boolean
  wechat_template_status: string
}
```

接口只返回当前用户 `status = active` 的关注记录。企业即使没有开放岗位仍保留在列表，`openJobCount` 为 0，摘要显示“暂无开放岗位”。Logo 继续通过现有 CloudRun 资源水合流程处理，避免每项单独请求详情。

### 8.3 列表项和操作

每项展示：

- Logo、企业名称和行业。
- 最多两个真实开放岗位分类；没有时显示“暂无开放岗位”。
- “已关注”状态。
- “微信提醒已开启”或“微信提醒未开启”状态。
- 点击主体进入统一企业详情。
- 独立操作提供“开启提醒/关闭提醒”和“取消关注”。

取消关注必须二次确认。列表操作按钮与主体点击隔离，不能误入企业详情。

空状态文案为“关注企业后，可在这里集中管理岗位更新”，并提供“浏览企业”入口，使用 `switchTab` 返回企业页。

## 9. 关注与微信提醒状态机

### 9.1 状态定义

有效状态组合：

| 关注 | 微信提醒 | 含义 |
| --- | --- | --- |
| 否 | 否 | 未关注 |
| 是 | 否 | 已关注，未接收微信提醒 |
| 是 | 是 | 已关注并接收微信提醒 |

不存在“未关注但提醒开启”的有效状态。

### 9.2 操作规则

- 关注企业：创建或激活关注记录；默认 `wechat_enabled = false`，不得恢复历史提醒授权。
- 开启提醒：必须先存在有效关注，再调用微信订阅授权和提醒接口。
- 用户拒绝、取消或系统不可用：保留关注，只更新相应模板状态，不回滚关注。
- 关闭提醒：设置 `wechat_enabled = false`，保留关注记录。
- 取消关注：服务端在同一事务中设置 `status = inactive`、`wechat_enabled = false`、`wechat_template_status = not_requested`；成功后从关注页移除。
- 重新关注：继续保持提醒关闭，用户必须再次主动开启提醒。

现有 `CompanyFollowAction` 继续承载关注/取关确认；`WechatReminderAction` 继续承载提醒授权。企业详情当前将“取消订阅”与取关绑定的逻辑必须拆开，改为复用两个独立组件或相同状态机。

### 9.3 客户端同步

- 服务端是关注和提醒状态的权威来源。
- 操作成功后通过现有 `company-follow-state` 事件同步 Match、企业目录、详情和关注页。
- 关闭提醒事件必须表达 `followed: true, reminderEnabled: false`。
- 取消关注事件表达 `followed: false, reminderEnabled: false`。
- 操作失败时恢复原状态，不发送成功事件。

## 10. 加载、异常与降级

### 10.1 岗位详情

- 加载成功但无公开申请方式：展示稳定空态，不把企业联系人当作替代申请入口。
- 复制失败：保留原内容，提示稍后重试。

### 10.2 企业联系人

- 新客户端连接旧后端、只有 `contactCount`：显示“已收录联系人，升级会员后可查看”，不伪造姓名/title。
- `contactPreviews` 存在：渲染脱敏列表。
- 有权限却未返回完整联系人：显示“联系人信息暂时无法加载”并支持页面重试，不降级展示缓存中的敏感信息。
- `contactCount = 0`：显示无联系人空态。

### 10.3 关注管理

- 首次加载失败：完整错误态与重试。
- 列表已加载后的刷新失败：保留现有列表并提示刷新失败。
- 单项提醒操作失败：恢复原提醒状态。
- 取消关注失败：保留该企业并恢复操作按钮。
- 企业已被停用或删除：列表项允许取消关注；详情入口提示企业资料不可用。

## 11. 视觉与可访问性

本次沿用 `docs/haigoo-mini-design-system.md` 的暖橙、深墨和冷灰体系，不建立新主题。

- 企业详情继续使用当前企业目录入口的视觉结构，不为 Match 入口创建变体。
- 联系人预览与完整联系人使用同一信息层级；锁定态通过图标、文案和操作共同表达，不只依赖灰色或模糊效果。
- 关注管理页采用紧凑企业列表，不嵌套大卡片，不抢占底部安全区。
- 公开申请方式、联系人复制、提醒开关和取消关注的触控区域至少 `88rpx`。
- 所有图标按钮提供明确的 `aria-label`，状态变化有文字反馈。
- 姓名和 title 支持两行或合理截断；320px 宽度下操作按钮不挤压企业名称。
- 页面遵循微信导航栏、胶囊和底部安全区，不覆盖系统返回手势区域。

## 12. 组件与文件边界

预计修改或新增的主要边界：

- `cloudrun/company-directory.mjs`：保持公开申请方式映射，补充相关测试。
